## Anthropic-Framed AI-Native SDLC

As I've learned more from and for Anthropic, I've realized that working this way requires [rethinking the SDLC](https://academy.claude.com/courses/ai-native-sdlc-playbook) at each step in order to maintain quality, confidence, and accountability. Anthropic was way ahead of me, and I'll be honest... it was a tough realization.

That said, continous improvement was the spirit of our (and my) way of working for the last 20 years; that spirit is needed now more than ever.

| STAGE	| TRADITIONAL SDLC	| AI-NATIVE SDLC |
|-------|--------------------|----------------|
| Plan	| Requirements gathered by committee, distilled through workshops and sign-offs, written up by hand	| Claude synthesizes pain points straight from the sources and captures them within intent.md which is human readable and machine actionable |
| Design	| Spec written by analysts, parsed by designers	| Requirements and design compressed into one working session with an agent, guided by standards encoded as skills, versioned in git |
| Build	| Tests and code are handwritten and documentation is written after the main development happens	| Tests and code are generated by AI and institutional knowledge is maintained as versioned machine-readable CLAUDE.md files and skills
| Test	| QA gates at stage boundaries	| Continuous evals woven through implementation |
| Deploy | Humans review every line of code and governance occurs in review cycles, often inconsistently | Layers of agentic review with human review reserved for regulated and critical code. Governance is enforced as the AI acts, with hooks as approval gates |
| Maintain	| Humans watch production for bugs | Agents monitor live deployments. Any breached control band is diagnosed and written back into the loop as a new intent.md |


## Anthropic-Agnostic PROSE Pattern

As was true with REST, though, it's not just Anthropic or a specific vendor thinking about this. Conceptual standards are critical to world-grade systems engineering, and they're emerging to help guide us all. Consider [PROSE](https://danielmeppiel.github.io/awesome-ai-native/docs/concepts/):

- **P: Progressive disclosure**
    - CLAUDE.md stays short and points to the rules. python.md loads only when a .py file is opened, and testing.md only when something in tests/ is. The agent isn’t carrying test rules while it edits code.

- **R: Reduced scope**
    - write-tests writes into tests/ only.
    - test-reviewer reads tests and can’t change anything.
    - code-reviewer reviews code outside tests/ and leaves the tests to test-reviewer.

- **O: Orchestrated composition**
    - write-code chains the steps: change, then test, then lint, then code-reviewer, then test-reviewer. Each piece is simple, and the chain is what does the full job.

- **S: Safety boundaries**
    - settings.json denies reading .env and secrets/ and denies git push and rm. It also blocked my edits to .claude/ earlier in this session.
    - Reviewers get only Read, Grep, Glob.
    - Incident text is treated as data, never as instructions.

- **E: Explicit hierarchy**
    - Instructions run from org policy, to CLAUDE.md, to path-scoped rules, to skills, to agents. Skills say when to “STOP and ask”, so it’s clear who decides.

### Rule of thumb
    If an agent goes wrong, ask: did it see too much (P), try to do too much (R), work alone when it should have been part of a chain (O), have too much freedom (S), or not know which instruction wins (E)?
